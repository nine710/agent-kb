## Options

### Option A: 管理者模式

由管理者 Agent 分解任务、分派执行者、汇总结果并决定后续控制流。全局优先级、资源分配和结果整合集中在一个协调节点。

### Option B: 对等协作

多个 Agent 直接相互审查、协商和迭代改进，不预设唯一的控制中心。它把制衡和交叉验证分散到协作成员之间。

### Option C: 去中心化移交

Agent 根据能力、状态或协议直接把任务移交给下一位合适的协作者。控制权随任务状态流动，而非长期固定在管理者或对等群体中。

## Tradeoffs

| | 优势 | 代价 |
|---|---|---|
| A 管理者 | 全局调度、优先级和汇总责任明确 | 管理者会成为瓶颈或单点错误来源，错误可能向下游级联 |
| B 对等 | 可形成交叉审查和迭代改进，减少单一判断偏差 | 协商、终止和一致性成本更高，需要明确责任边界 |
| C 去中心化移交 | 控制权可随能力和状态动态转移，避免长期中心依赖 | 路由、可观测性和失败恢复更复杂，移交协议设计决定可靠性 |

## Apply to Agent Development

- 任务有明确总计划、资源约束或最终汇总责任时选 A，并让管理者验证关键中间结果。
- 需要独立审查、互相质疑或多轮改进时选 B，先定义各方的终止条件和裁决规则。
- 任务流会在不同专长间动态切换时选 C，为移交定义状态、所有权和失败回退。
- 上下文共享与否是另一条独立决策轴：任何拓扑都可以使用共享上下文或通过文件、消息等工件通信。
- 无论采用哪种拓扑，都要将共享工件并发、错误传播和控制权移交设计为可观察、可验证的机制。

## Development Agent Procedure

### Trigger

在单 Agent 不足以完成分工、独立审查、结果汇总或跨专长移交的任务，且必须指定控制权和信息流时，读取本卡。若拆分不能降低风险或扩大可验证能力，则不应触发多 Agent 设计。

### Decision Inputs

记录是否存在统一计划和最终汇总责任、是否需要独立互审、任务是否会按能力和状态动态流转、上下文是否共享、共享工件的写入冲突风险、失败传播范围、终止条件和恢复负责人。

### Option Relationship

A、B、C 是主控制拓扑的互斥选择：一个协作单元必须明确由管理者集中调度、由对等成员协商，或按协议去中心化移交。共享上下文与否、文件/消息通信是独立的信息流轴，可与任一拓扑组合，不能被误当作第四种控制拓扑。

### Selection Rules

- 有全局计划、资源约束、最终整合责任或统一质量门时选择 A，并让管理者验证关键中间结果。
- 主要价值来自独立质疑、交叉审查和迭代改进时选择 B，并预先定义终止、冲突裁决和责任边界。
- 任务会按专长或状态动态交接时选择 C，并定义所有权、最小移交状态和失败回退。
- 共享工件时，为每个写入者定义所有权或串行化规则；复杂度超过单 Agent 的收益时停止拆分。

### Required Artifacts

交付协作拓扑图、角色/所有权矩阵、任务状态与控制权转移协议、共享上下文或文件/消息接口、终止与冲突裁决规则、错误升级与恢复路径，以及每项共享工件的并发写入约定。

### Verification

- 演练正常完成、执行者失败、管理者错误、对等分歧或移交超时等路径，确认任务不会丢失、重复或无终止循环。
- 对共享文件和消息执行并发冲突测试，确认所有权/版本规则会阻止覆盖。
- 追踪每次控制权转移和关键中间结果，检查错误不会未经验证地级联到下游。
- 比较单 Agent 基线，确认拆分带来的可验证性或能力收益高于通信与协调成本。

## Anti-Patterns

- 让管理者只转发子 Agent 文本，却不验证中间结果和错误传播。
- 在对等协作中没有终止条件、责任边界或冲突裁决，导致循环协作。
- 在去中心化移交中不记录任务所有权和状态，导致任务丢失或重复执行。
- 让多个 Agent 在共享文件系统中无所有权约定地并发写同一工件。
- 为了“多 Agent”而拆分一个单 Agent 已能可靠完成的任务，只增加通信成本。
