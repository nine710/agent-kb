## Options

### Option A: 管理者模式

由管理者 Agent 分解任务、分派执行者、汇总结果并决定后续控制流。全局优先级、资源分配和结果整合集中在一个协调节点。

### Option B: 对等协作

多个 Agent 直接相互审查、协商和迭代改进，不预设唯一的控制中心。它把制衡和交叉验证分散到协作成员之间。

### Option C: 去中心化移交

Agent 根据能力、状态或协议直接把任务移交给下一位合适的协作者。控制权随任务状态流动，而非长期固定在管理者或对等群体中。

## Tradeoffs

| | 优势 | 代价 |
|---|---|---|
| A 管理者 | 全局调度、优先级和汇总责任明确 | 管理者会成为瓶颈或单点错误来源，错误可能向下游级联 |
| B 对等 | 可形成交叉审查和迭代改进，减少单一判断偏差 | 协商、终止和一致性成本更高，需要明确责任边界 |
| C 去中心化移交 | 控制权可随能力和状态动态转移，避免长期中心依赖 | 路由、可观测性和失败恢复更复杂，移交协议设计决定可靠性 |

## Apply to Agent Development

- 任务有明确总计划、资源约束或最终汇总责任时选 A，并让管理者验证关键中间结果。
- 需要独立审查、互相质疑或多轮改进时选 B，先定义各方的终止条件和裁决规则。
- 任务流会在不同专长间动态切换时选 C，为移交定义状态、所有权和失败回退。
- 上下文共享与否是另一条独立决策轴：任何拓扑都可以使用共享上下文或通过文件、消息等工件通信。
- 无论采用哪种拓扑，都要将共享工件并发、错误传播和控制权移交设计为可观察、可验证的机制。

## Anti-Patterns

- 让管理者只转发子 Agent 文本，却不验证中间结果和错误传播。
- 在对等协作中没有终止条件、责任边界或冲突裁决，导致循环协作。
- 在去中心化移交中不记录任务所有权和状态，导致任务丢失或重复执行。
- 让多个 Agent 在共享文件系统中无所有权约定地并发写同一工件。
- 为了“多 Agent”而拆分一个单 Agent 已能可靠完成的任务，只增加通信成本。
