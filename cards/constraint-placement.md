## Options

### Option A: 系统提示词常驻（Constitution / 岗位说明书）

把**可语言化**的规则写进系统提示词（即 CLAUDE.md 类的 constitution），作为静态前缀在每次推理时拼在轨迹之前。系统提示词由开发者编写、在整个对话中保持不变，相当于 Agent 的"岗位说明书"——定义身份、权限和行为准则。模型对 `system` 位置的指令遵循能力最强（训练时大量使用了该位置的指令），因此同样一条规则写在这里执行效果最好。

### Option B: Skills 按需加载（渐进式披露）

把领域能力/规则模块化为独立的 Agent Skill，采用渐进式披露：第一层只把每个 Skill 的元数据（`name` + `description`，通常数百 token）常驻注入，供模型做路由判断；第二层在被选中后通过专用 Skill 工具加载完整 `SKILL.md`，内容作为 tool result 出现在上下文中间；第三层按需引用更细的子文档。静态前缀（system prompt + 工具定义）始终不变，因此对 KV Cache / Prompt Cache 友好（"一次性写入、永久受益"），解决"把所有规则塞进单一提示词→浪费 token + 注意力稀释"的问题。

### Option C: Harness 程序强制（护栏 / 默认拒绝 / 验证）

把**确定性流程与约束**写成程序和 Harness——模型无法省略、不可绕过：故障安全默认值（所有能力默认关闭、必须显式开放，如 Claude Code 中每个工具默认需要用户授权才能执行）；工具调用时的风险评级与执行侧校验（校验结构化数据而非模型自由文本）；以及分层护栏（输入侧分类器/正则过滤、执行侧工具风险评级、输出侧 PII 过滤与输出验证）。它属于 Harness 的"约束 / 验证 / 纠正"层，与"上下文 / 工具"层并列，是单靠文本约束之外的、非建议性的强制层。

### Option D: 专用工具 + 人在回路（高风险门）

把高风险、不可逆或强业务约束的操作（支付、删除数据、发送邮件、生产部署）封装为参数明确、权限受限、全程可审计的**专用工具**，必要时加上预览与人工确认（Human in the loop）；当超过失败阈值或命中高风险操作时把控制权升级给人。这里的约束体现在"动作接口的形状"（防呆式 ACI）和"审批门"，而非文本规劝或静默的代码校验——对不可逆动作提供最后一道由人判断的关口。

## Tradeoffs

| | 优势 | 代价 |
|---|---|---|
| A 常驻 | 指令遵循最强（system 位）；全场景一致生效；实现最简单 | 上下文膨胀、注意力被稀释；任何改动都破坏 KV Cache 前缀→延迟与成本飙升；规则以无序方式堆砌时模型难辨优先级（消融：打乱信息组织→任务成功率降 >30%） |
| B 按需 | 前缀稳定→缓存友好（一次写入、永久受益）；上下文只装载相关能力；Skill 可独立开发、版本化、分享 | 强依赖路由准确度（`description` 要像"Use when / Don't use when" + 反例，缺反例→误触发显著上升）；指令落在上下文中间→对模型 instruction-following 要求高，模型间差异大；多一次工具加载往返 |
| C 程序强制 | 模型无法绕过，可靠性最高；确定性、可审计；不占用语义注意力 | 只适合能形式化的约束，不适合"可语言化策略"；开发与维护成本高；过度约束会扼杀模型自主性；阈值设错会误拦合法任务 |
| D 工具 + HITL | 对不可逆操作最稳；保留人的最终判断；窄接口本身即防呆 | 引入人工成本与延迟；打断自主性、降低通量；确认门槛太高则动辄求确认、太低则形同虚设 |

## Apply to Agent Development

- **先按约束性质归类，再选承载位**：可语言化的策略 → Prompt 或 Skill；确定性流程与约束 → 程序和 Harness。这是源给出的总纲，先判性质再分层。
- **默认安全**：故障安全默认值——所有能力默认关闭、必须显式开放。映射到编程智能体即 pre-tool 授权门 / hooks / constitution 的"未授权不做"。
- **常驻(A) 还是按需(B) 看变更频率与上下文成本**：稳定且全场景适用的进静态前缀；按场景/领域且会持续膨胀的进 Skill，避免静态前缀被反复改写而击穿缓存。
- **提示词内的规则要"流程驱动"而非"规则堆砌"**：给标准操作流程（SOP）和优先级，否则多条规则同时适用时模型困惑。
- **Skill 路由按路由条件写**：`description` 写"何时该用我"并配反例，而非功能介绍；缺少反例会让路由准确率明显下降。
- **不可逆/高风险操作不要只靠文本约束**：必须升级到 C 或 D（代码强制或人工门），不能指望模型每次自觉遵守一句话。
- **对齐模型厂商的训练方法论**：用 Claude 这类模型时充分使用 Skills 与结构化系统提示（同一生态内天然最优），换模型则换用该模型厂商优化过的交互约定。
- **约束、验证、纠正是闭环**：缺任一环就有可靠性缺口；不要只加约束而不做验证与纠正。

## Anti-Patterns

- 把所有规则塞进单一系统提示词（规则堆砌 + 持续膨胀）→ 注意力稀释、缓存反复失效。
- 动态系统提示词（每次把时间戳、余额等注入 `system`）→ 每次请求都破坏 KV Cache 前缀；正确做法是放到上下文末尾（状态栏）或按需用工具获取。
- 工具定义动态重排、或逐请求挑选"最相关"的 few-shot 示例 → 改写前缀、缓存持续失效。
- 用滑动窗口丢弃历史 → 既破坏前缀一致性，又会丢失关键工具结果、使 Agent 陷入重复调用循环。
- Skill 的 `description` 写成"我能做什么"且不带反例 → 宽泛描述在不相关任务上频繁误触发。
- 高风险操作只靠系统提示词里一句"不要做 X"，而无代码门或人工确认 → 模型仍可能越界。
- 把可形式化的安全校验（如退款金额不超过订单金额）交给模型自觉，而非代码校验 → 留下可靠性缺口。
- 只依赖单一护栏 → 应做成分层防御，单个护栏不足以提供足够保护。
- 给模型过大的业务自由裁量权 → 业务规则必须细化到可执行，规则模糊会使行为不可预测。
