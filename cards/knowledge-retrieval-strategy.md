## Options

### Option A: 稠密语义检索

将内容分块并编码为稠密向量，根据语义相似度检索片段。它以概念关联为主要信号，适合用户措辞和原文术语不完全一致的知识请求。

### Option B: 稀疏关键词检索

使用词项和关键词的精确匹配检索内容。它把可见术语、标识符和罕见名称作为主要信号，适合 Agent 需要找到确切 API、错误码、文件名或配置键的情形。

### Option C: 混合检索

同时使用稠密语义信号和稀疏精确匹配，再融合或重排结果。它把语义召回与符号精度作为并行能力，而非迫使一种检索方式覆盖所有查询。

### Option D: 结构化索引

用实体关系、字段、目录层级或其他显式结构组织知识，再沿结构定位内容。它让 Agent 按组件、依赖、所有权或时间关系访问知识，而不是只在扁平文本块中相似度搜索。

## Tradeoffs

| | 优势 | 代价 |
|---|---|---|
| A 稠密 | 能处理同义表达和概念关联，适合自然语言问题 | 对精确标识符和相近概念的区分可能不足；分块和嵌入质量决定上限 |
| B 稀疏 | 对 API 名、错误码和专有术语可预测且精确 | 难覆盖表达变化、隐含概念和跨词汇关联 |
| C 混合 | 同时覆盖语义召回和精确匹配，降低单一信号漏检 | 需要融合、排序和评估，索引与运行成本更高 |
| D 结构化 | 对关系、层级和治理要求强的知识可解释、可维护 | 建模和维护成本高；结构过时或不完整时会限制访问 |

## Apply to Agent Development

- 自然语言需求与原始文档措辞差异大时优先 A；把分块边界设计成可独立理解的知识单元。
- 查询经常含精确符号、文件路径、函数名或错误码时优先 B。
- 两类查询都重要且漏检代价高时采用 C，并对融合结果建立评估集，而不是假设混合一定更好。
- 代码库、设计规范或长期知识存在明确组件关系和目录层级时采用 D，必要时让检索先走结构再读取文本。
- 无论采用何种检索，都治理时效和冲突；检索质量是知识型 Agent 能力上限的一部分。

## Anti-Patterns

- 把全部知识扁平切块后只依赖单一相似度分数，忽略精确标识符和结构关系。
- 让 chunk 跨越多个不相关主题，导致检索到片段却无法形成可执行上下文。
- 用稀疏检索处理大量同义表达，却不评估漏召回。
- 引入混合检索但不验证融合规则，实际只增加复杂度和延迟。
- 不治理过期和冲突的知识库，使 Agent 检索到旧规则或相互矛盾的内容。
